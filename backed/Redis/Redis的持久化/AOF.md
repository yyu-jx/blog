## 三种写回策略

Redis 写入 AOF 日志的过程，如下图：


![image.png](https://gcore.jsdelivr.net/gh/yyu-jx/blog-images@main/images/20261125211820928.png)

我先来具体说说：

1. Redis 执行完写操作命令后，会将命令追加到 server.aof_buf 缓冲区；
2. 然后通过 write() 系统调用，将 aof_buf 缓冲区的数据写入到 AOF 文件，此时数据并没有写入到硬盘，而是拷贝到了内核缓冲区 page cache，等待内核将数据写入硬盘；
3. 具体内核缓冲区的数据什么时候写入到硬盘，由内核决定。

Redis 提供了 3 种写回硬盘的策略，控制的就是上面说的第三步的过程。

在 redis.conf 配置文件中的 appendfsync 配置项可以有以下 3 种参数可填：

- Always，这个单词的意思是「总是」，所以它的意思是每次写操作命令执行完后，同步将 AOF 日志数据写回硬盘；
- Everysec，这个单词的意思是「每秒」，所以它的意思是每次写操作命令执行完后，主线程先通过 write() 将命令写入到 AOF 文件的内核缓冲区（page cache），然后由一个 **BIO 后台线程**每隔一秒异步调用 fsync()，把内核缓冲区的内容写回到硬盘；
- No，意味着不由 Redis 控制写回硬盘的时机，转交给操作系统控制写回的时机，也就是每次写操作命令执行完后，先将命令写入到 AOF 文件的内核缓冲区，再由操作系统决定何时将缓冲区内容写回硬盘。

## AOF 重写机制

Redis 为了避免 AOF 文件越写越大，提供了 **AOF 重写机制**，当 AOF 文件的大小超过所设定的阈值后，Redis 就会启用 AOF 重写机制，来压缩 AOF 文件。

AOF 重写机制是在重写时，读取当前数据库中的所有键值对，然后将每一个键值对用一条命令记录到「新的 AOF 文件」，等到全部记录完后，就将新的 AOF 文件替换掉现有的 AOF 文件。

举个例子，在没有使用重写机制前，假设前后执行了「set name xiaolin」和「set name xiaolincoding」这两个命令的话，就会将这两个命令记录到 AOF 文件。

![image.png](https://gcore.jsdelivr.net/gh/yyu-jx/blog-images@main/images/20261125213611952.png)
在使用重写机制后，就会读取 name 最新的 value（键值对） ，然后用一条 「set name xiaolincoding」命令记录到新的 AOF 文件

## 写时复制（Copy On Write，COW）

### 1. 什么是写时复制？

写时复制（Copy On Write，COW）是一种延迟复制技术。

**核心思想：多个进程先共享同一份物理内存，只有当某个进程真正修改共享内存时，操作系统才复制被修改的内存页。**

这样可以避免创建子进程时立即复制大量物理内存，从而节省内存资源和创建时间。

### 2. COW 的实现原理

以 Redis 为例：

1. Redis 主进程通过 `fork()` 创建子进程。
    
2. 操作系统为子进程创建独立的虚拟地址空间和页表，但父子进程的页表暂时指向相同的物理内存页。
    
3. 这些共享内存页会被设置为只读，防止父子进程直接修改共享数据。
    
4. 当父进程或子进程尝试修改共享内存时，CPU 触发写保护异常。
    
5. 操作系统将需要修改的物理内存页复制一份，并更新修改方的页表映射。
    
6. 修改方在新的物理内存页上执行写操作，而另一方仍然使用原来的物理内存页。
    

### 3. 举例说明

假设 Redis 主进程中有以下数据：

```
name = zhangsan
age = 18
```

**（1）fork 创建子进程后**

父子进程拥有各自的页表，但暂时指向同一份物理内存：

```
父进程页表 ──┐
             ├──> 物理页 A
子进程页表 ──┘     name = zhangsan
                   age = 18
```

**（2）主进程修改数据**

主进程执行：

```
SET name lisi
```

由于物理页 A 是共享且只读的，操作系统触发写时复制：

```
父进程页表 ─────> 物理页 B
                  name = lisi
                  age = 18

子进程页表 ─────> 物理页 A
                  name = zhangsan
                  age = 18
```

此时父子进程拥有独立的数据，互不影响。

### 4. 为什么 Redis 使用 COW？

Redis 在执行 RDB 持久化或 AOF 后台重写时，需要通过 `fork()` 创建子进程。

子进程负责读取数据库数据，生成持久化文件；主进程继续处理客户端请求。

使用 COW 可以：

- 避免 fork 时立即复制整个 Redis 数据库，节省内存。
    
- 子进程读取 fork 时刻的数据快照，不受主进程后续修改的影响。
    
- 主进程可以继续处理客户端请求，减少阻塞。
    

### 5. COW 可能带来的问题

虽然 COW 减少了 fork 时的内存复制，但仍然存在性能开销：

- **fork 阶段：** 需要复制页表等数据结构，Redis 数据规模越大，可能产生越长的短暂阻塞。
    
- **写时复制阶段：** 父子进程修改共享内存页时，需要复制物理内存页，复制的数据越多，开销越大。
    

注意：COW 是以内存页为单位进行复制的，而不是直接复制整个 Redis Key。

### 6. 总结

COW 的核心就是：**先共享，后复制；谁修改，谁复制。**

- 虚拟地址：进程使用的内存地址。
    
- 物理地址：真实 RAM 中的内存地址。
    
- 页表：记录虚拟内存页与物理内存页框之间的映射关系。
    
- COW：修改共享内存页时，复制对应内存页，并更新修改方的页表映射。


### 7.COW 的三个好处：
1. 减少内存占用： 父子进程共享物理内存，不需要立即保存两份完整数据。
2. 减少创建子进程的开销： fork 时不需要复制全部内存数据。
3. 保证数据隔离： 修改时复制对应内存页，父子进程互不影响。

## Redis 7.0 引入的 Multi Part AOF（MP-AOF）

改变了重写期间增量命令的保存方式：

- Redis 7.0 之前：通过 AOF 重写缓冲区保存增量命令。
- Redis 7.0 之后：通过新的 incr 文件保存增量命令。

1. 重写开始时，主进程先打开一个新的 incr 文件，之后新的写命令会直接追加到这个新的 incr 里，而不再写入「AOF 重写缓冲区」；
2. 子进程负责把当前内存状态以 RDB 格式写入到一个新的 base 文件；
3. 重写完成后，Redis 只需原子地更新 manifest 文件，让它指向新的 base 和新的 incr 即可，旧的 base 和旧的 incr 可以安全删除。
