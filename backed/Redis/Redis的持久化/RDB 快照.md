
# RDB 快照

- AOF 文件的内容是操作命令；
- RDB 文件的内容是二进制数据。

RDB 快照就是记录某一个瞬间的内存数据，记录的是实际数据，而 AOF 文件记录的是命令操作的日志，而不是实际的数据
****

Redis 提供了两个命令来生成 RDB 文件，分别是 save 和 bgsave，他们的区别就在于是否在「主线程」里执行：

• 执行了 save 命令，就会在主线程生成 RDB 文件，由于和执行操作命令在同一个线程，所以如果写入 RDB 文件的时间太长，会阻塞主线程；
• 执行了 bgsave 命令，会创建一个子进程来生成 RDB 文件，这样可以避免主线程的阻塞；

RDB 文件的加载工作是在服务器启动时自动执行的，Redis 并没有提供专门用于加载 RDB 文件的命令。

Redis 还可以通过配置文件的选项来实现每隔一段时间自动执行一次 bgsave 命令，默认会提供以下配置：
```
save 900 1
save 300 10
save 60 10000
```

别看选项名叫 save，实际上执行的是 bgsave 命令，也就是会创建子进程来生成 RDB 快照文件。
只要满足上面条件的任意一个，就会执行 bgsave，它们的意思分别是：

• 900 秒之内，对数据库进行了至少 1 次修改；
• 300 秒之内，对数据库进行了至少 10 次修改；
• 60 秒之内，对数据库进行了至少 10000 次修改。

这里提一点，Redis 的快照是全量快照，也就是说每次执行快照，都是把内存中的「所有数据」都记录到磁盘中。
****

## Redis RDB 持久化中的 COW

### 1. 为什么使用 COW？

Redis 执行 `BGSAVE` 时，需要创建子进程来生成 RDB 文件。

如果 fork 时直接复制整个 Redis 内存数据，会产生较大的时间和内存开销。

因此 Redis 使用 COW（Copy On Write，写时复制）：

- fork 时，父子进程暂时共享相同的物理内存页。
    
- 父子进程拥有各自独立的页表。
    
- 只有某个进程尝试修改共享内存页时，操作系统才复制对应的物理内存页。
    

这样可以减少创建子进程时的开销和内存占用。

### 2. BGSAVE 期间发生写操作怎么办？

假设 fork 时 Redis 数据为：

```
name = zhangsan
age = 18
```

子进程开始生成 RDB 文件。

此时客户端执行：

```
SET name lisi
```

主进程需要修改数据，但不能影响子进程正在读取的快照数据。

于是触发 COW：

1. 操作系统复制对应的物理内存页。
    
2. 更新主进程的页表，让它指向新的物理内存页。
    
3. 子进程仍然指向原来的物理内存页。
    
4. 主进程在新的物理内存页上完成修改。
    

最终：

- 主进程看到 `name=lisi`。
    
- 子进程仍然看到 `name=zhangsan`。
    

### 3. RDB 快照保存哪个时间点的数据？

RDB 保存的是执行 fork 时刻的数据快照。

快照期间主进程发生的修改不会进入本次 RDB，需要等待下一次快照才能持久化。

如果 Redis 在下一次快照完成之前崩溃，那么本次快照之后的修改可能丢失。

### 4. COW 的内存开销

fork 刚完成时，父子进程共享物理内存页。

随着主进程不断修改数据，越来越多的共享内存页可能被复制。

极端情况下，如果原本共享的内存页全部被修改，内存占用可能接近原来的两倍。

因此，需要关注 BGSAVE 期间的写操作频率和内存使用情况。

### 5. 核心总结

- COW：保证父子进程修改数据时互不影响。
    
- BGSAVE：子进程负责生成 RDB，主进程继续处理请求。
    
- RDB：保存 fork 时刻的数据快照，而不是实时最新数据。
    

**记忆口诀：fork 定快照，子进程读旧数据，主进程改新数据，COW 保证互不影响。**
