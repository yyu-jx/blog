
# Redis 大 Key 对持久化有什么影响？


## 大 Key 对 AOF 日志的影响

Redis 提供了 **3 种 AOF 日志写回硬盘的策略**，分别是：

- Always，这个单词的意思是「总是」，所以它的意思是每次写操作命令执行完后，同步将 AOF 日志数据写回硬盘；
- Everysec，这个单词的意思是「每秒」，所以它的意思是每次写操作命令执行完后，先将命令写入到 AOF 文件的内核缓冲区，然后每隔一秒将缓冲区里的内容写回到硬盘；
- No，意味着不由 Redis 控制写回硬盘的时机，转交给操作系统控制写回的时机，也就是每次写操作命令执行完后，先将命令写入到 AOF 文件的内核缓冲区，再由操作系统决定何时将缓冲区内容写回硬盘。
****

在**使用 Always 策略**的时候，主线程在执行完命令后，会把数据写入到 AOF 日志文件，然后会调用 fsync() 函数，将内核缓冲区的数据直接写入到硬盘，等到硬盘写操作完成后，该函数才会返回。
当使用 Always 策略的时候，如果写入是一个大 Key，主线程在执行 fsync() 函数的时候，阻塞的时间会比较久，因为当写入的数据量很大的时候，数据同步到硬盘这个过程是很耗时的。

当**使用 Everysec 策略**的时候，由于 fsync() 是由后台 BIO 线程异步执行的，所以相比 Always 策略，大 Key 持久化对主线程的影响会显著减轻。但需要注意的是，主线程仍然要同步执行 write() 把 AOF 缓冲区的数据拷贝到内核缓冲区，写入大 Key 时 write() 本身的耗时也会随之变大；并且如果上一次后台 fsync() 还未结束，主线程的 write() 会被强制等待，此时大 Key 依然可能对主线程造成阻塞。

当**使用 No 策略**的时候，由于永不执行 fsync() 函数，所以大 Key 持久化的过程不会影响主线程。
****

## Redis 大 Key 对 AOF 重写和 RDB 的影响

### 一、核心问题

Redis 执行 AOF 重写和 RDB 快照时，都需要通过 `fork()` 创建子进程。

- AOF 重写：子进程根据当前 Redis 数据生成新的 AOF 文件。
    
- RDB 快照：子进程将某一时刻的 Redis 数据生成 RDB 文件。
    

虽然持久化工作由子进程完成，但 `fork()` 是由 Redis 主线程调用的，因此 fork 耗时过长会阻塞主线程，导致 Redis 暂时无法处理客户端命令。
****
### 二、fork() 为什么会受到大 Key 的影响？

#### 1. fork 的内存处理机制

Redis 执行 fork 时，操作系统不会立即复制父进程的全部物理内存，而是：

1. 复制父进程的页表等必要的数据结构。
    
2. 父子进程的虚拟内存暂时映射到相同的物理内存。
    
3. 对共享内存页设置写保护，配合 COW 机制。
    

因此，fork 不需要立即复制全部物理内存，但仍然需要复制页表。

#### 2. 页表是什么？

页表是操作系统维护的数据结构，用于记录虚拟地址与物理地址之间的映射关系。

可以理解为：

**页表就是虚拟地址和物理内存地址之间的映射字典。**

#### 3. 大 Key 为什么会影响 fork？

大 Key 增多，可能导致 Redis 内存占用增加。

Redis 管理的内存页越多，通常页表规模也越大。

fork 时需要复制页表等数据结构，因此：

大 Key 增多 → Redis 内存占用增加 → 内存页数量增加 → 页表变大 → fork 耗时增加 → Redis 主线程阻塞。

注意：真正影响页表大小的是内存映射的页数量，而不是 Key 的数量本身。
****
### 三、什么是写时复制 COW？

COW 全称 Copy On Write，即写时复制。

#### 1. 为什么需要 COW？

fork 创建子进程后：

- 父进程继续处理客户端请求。
    
- 子进程负责持久化，需要读取 fork 时刻的数据。
    

如果父进程修改了共享内存，可能影响子进程读取的数据，导致快照不一致。

因此，操作系统使用 COW 机制，让父子进程暂时共享物理内存。

#### 2. COW 的执行过程

1. fork 完成后，父子进程共享物理内存页。
    
2. 共享内存页被设置为只读。
    
3. 父进程尝试修改共享内存。
    
4. CPU 发现写入违反内存权限，触发写保护异常。
    
5. 操作系统内核复制对应的物理内存页。
    
6. 修改父进程的内存映射，让父进程指向新的物理内存页。
    
7. 父进程完成写操作，子进程继续读取原来的数据。
    

#### 3. COW 为什么会造成性能问题？

COW 是以内存页为单位进行复制的。

如果父进程修改的数据涉及很多内存页，就可能产生大量内存复制开销。

因此：

大 Key 增多 → 修改涉及的内存页可能增多 → COW 复制开销增加 → Redis 写操作可能变慢。

注意：不是修改一个大 Key 就复制整个 Key，而是复制实际受到写操作影响的内存页。

****

### 四、Linux 内存大页对 Redis 的影响

#### 1. 什么是内存大页？

Linux 普通内存页通常为 4KB。

Transparent Huge Pages（THP，透明大页）支持使用 2MB 大小的内存页。

两者对比：

- 普通内存页：4KB。
    
- 透明大页：2MB。
    

#### 2. 为什么会影响 COW？

COW 以内存页为单位进行复制。

如果使用 2MB 大页，那么发生大页级别的 COW 时，可能需要复制 2MB。

如果使用普通 4KB 内存页，则只需要复制对应的 4KB 内存页。

计算：

2MB / 4KB = 512

因此，单次受影响内存页的复制量可能扩大 512 倍，增加内存复制开销，影响 Redis 性能。

#### 3. 如何关闭 THP？

执行：

```
sudo sh -c 'echo never > /sys/kernel/mm/transparent_hugepage/enabled'
```

查看状态：

```
cat /sys/kernel/mm/transparent_hugepage/enabled
```

出现 `[never]` 表示当前设置为关闭状态。

注意：运行时修改可能在系统重启后失效，需要配置开机持久化。
****
### 五、Redis 如何优化 fork 耗时？

#### 1. 控制单实例内存规模

尽量控制单个 Redis 实例的内存占用，例如参考 10GB 以下的经验建议，避免页表过大导致 fork 耗时增加。

#### 2. 纯缓存场景考虑关闭持久化

如果 Redis 只作为纯缓存使用，且数据可以从其他持久化数据源恢复，可以考虑关闭 AOF 和 RDB：

```
save ""
appendonly no
```

注意：其他需要 fork 的操作，例如主从复制全量同步，仍然可能发生。

#### 3. 合理调大 repl-backlog-size

`repl-backlog-size` 用于设置主节点复制积压缓冲区的大小。

如果缓冲区太小，从节点断开连接后，可能无法通过增量同步恢复数据，只能进行全量同步。

全量同步需要生成 RDB 文件，因此会调用 fork。

适当调大缓冲区，可以降低频繁全量同步的概率。



****
### 六、如何监控 fork 耗时？

执行：

```
INFO
```

查看：

```
latest_fork_usec:315
```

`latest_fork_usec` 表示最近一次 fork 操作的耗时，单位是微秒（μs）。

例如：

- 315μs = 0.315ms
    
- 1000000μs = 1s
    
- 1500000μs = 1.5s
    

如果 fork 耗时超过 1 秒，就需要重点排查。


****
### 七、总结：两个阶段可能造成阻塞

Redis 执行 AOF 重写或 RDB 快照时，有两个阶段需要特别关注：

**阶段一：创建子进程时**

fork 需要复制页表等数据结构。

Redis 内存越大，页表可能越大，fork 耗时可能越长。

**阶段二：创建子进程之后**

父进程修改共享内存时，可能触发 COW。

需要复制受到修改影响的物理内存页，复制量越大，开销可能越大。

最终记住：

- fork 阶段：主要关注页表复制。
    
- COW 阶段：主要关注物理内存页复制。
    
- THP：可能放大 COW 的内存复制粒度。
    
- 大 Key：可能同时增加上述两个阶段的性能压力。
    

**一句话总结：大 Key 不仅可能让 Redis 创建子进程变慢，还可能让持久化期间的写操作变慢。**
